## З1. Сервер PostgreSQL, роль, базы и файл `.env`

Преподаватель скажет, какой вариант запуска выбран для класса. Код приложения от варианта не зависит: оно находит базу по строке подключения в `.env`.

**Вариант А. Архив без установки** (скрипты в папке `db`, запускать из папки `server`):

1. Архив PostgreSQL 18 распакован в папку `%USERPROFILE%\pgsql` (внутри – `bin` с программами). Если путь другой, поправьте его в `db\db_env.bat`.
2. Один раз: `db\db_init.bat` – создает папку данных сервера `%USERPROFILE%\pgdata` и спрашивает пароль суперпользователя `postgres`. Запомните его.
3. Перед каждым занятием: `db\db_start.bat`. После занятия: `db\db_stop.bat`.
4. Один раз: `db\db_setup.bat ваш_пароль` – роль `pokrytie` с вашим паролем и базы `pokrytie`, `pokrytie_test` (скрипт `db/setup.sql`; сначала он спросит пароль `postgres`).
5. Консоль psql от имени `pokrytie`: `db\db_psql.bat`.

**Вариант Б. Контейнер Docker** (в папке `server`, Docker Desktop запущен):

1. Сначала создайте `.env` (шаг ниже): из него контейнер берет пароль роли.
2. `docker compose up -d` – запуск. Роль `pokrytie` и базы создаются сами при первом запуске.
3. Консоль psql: `docker compose exec db psql -U pokrytie -d pokrytie`.
4. После занятия: `docker compose down` (данные сохраняются).

**Файл `.env`.** Скопируйте `.env.example` в `.env` и замените `change_me` своим паролем во всех трех строках. Пароль – латинские буквы и цифры. Строка подключения устроена так:

```
postgresql://pokrytie:пароль@127.0.0.1:5432/pokrytie
            пользователь       адрес     порт  база
```

**Знакомство с psql.** Подключитесь и выполните команды: `\l` (список баз), `\conninfo` (куда подключены), `\dt` (таблицы; пока их нет), `SELECT version();`, `\q` (выход).

Проверка: `pytest tests/test_z1.py`, затем `fastapi dev app/main.py` и http://127.0.0.1:8000/api/health – приложение отвечает, к какой базе и от чьего имени подключено.

## З2. Повторение SQL: архив поездок

Загрузите архив – 40 поездок четырех автомобилей за октябрь 2026 года, таблица `archive_trips`:

- вариант А: `db\db_psql.bat -f data\archive.sql`
- вариант Б: `docker compose exec db psql -U pokrytie -d pokrytie -f /data/archive.sql`

Посмотрите на таблицу: `\d archive_trips` и `SELECT * FROM archive_trips LIMIT 5;`. Столбцы: `car` (бортовой номер), `date`, `distance` (км), `surface`, `avg_speed` (средняя скорость, км/ч), `rain` (шел ли дождь), `model_ok` (совпал ли прогноз модели с настоящим покрытием).

Напишите десять запросов, каждый в своем файле. Условие – в первой строке файла. Имена и порядок столбцов в ответе – как в условии; для вычисленных столбцов задайте имя через `AS`, как указано ниже.

| Файл | Что нужно | Повторяем |
| --- | --- | --- |
| `q01.sql` | поездки АВ-04 по снегу: `id, date, distance`, по дате | `WHERE ... AND ...`, `ORDER BY` |
| `q02.sql` | пять самых длинных поездок: `id, car, distance` | `ORDER BY ... DESC`, `LIMIT` |
| `q03.sql` | в дождь со скоростью больше 60: `id, car, avg_speed`, по номеру | логический столбец в `WHERE` |
| `q04.sql` | с 1 по 3 октября 2026 года включительно: `id, date, car`, по дате, затем по номеру | `BETWEEN` для дат |
| `q05.sql` | число поездок по покрытиям: `surface, trips`, по коду | `COUNT(*)`, `GROUP BY` |
| `q06.sql` | средний пробег автомобиля, до 0,1: `car, avg_distance`, от большего | `ROUND(AVG(...), 1)` |
| `q07.sql` | покрытия со средней скоростью меньше 50: `surface, avg_speed` (до 0,1), по коду | `HAVING` |
| `q08.sql` | доля ошибок модели по покрытиям в процентах, до 0,1: `surface, error_percent` | `COUNT(*) FILTER (WHERE ...)` |
| `q09.sql` | у АВ-03 7 октября был снег: исправить покрытие, вернуть `id, surface` | `UPDATE ... RETURNING` |
| `q10.sql` | удалить поездки короче 1 км, вернуть `id, distance` | `DELETE ... RETURNING` |

`COUNT(*) FILTER (WHERE условие)` – особенность PostgreSQL: считает только строки, для которых условие выполнено. Доля в процентах: `100.0 * ошибки / все`. Множитель `100.0`, а не `100`: иначе деление целых чисел отбросит дробную часть.

`RETURNING` после `INSERT`, `UPDATE`, `DELETE` возвращает затронутые строки: не нужно делать отдельный `SELECT`.

Запуск одного запроса: `db\db_psql.bat -f sql\q01.sql` (вариант Б: `docker compose exec db psql -U pokrytie -d pokrytie -f /sql/q01.sql`). Запросы q09 и q10 меняют архив; чтобы вернуть его, загрузите `archive.sql` еще раз. Тесты выполняют все запросы в транзакции и отменяют ее.

Проверка: `pytest tests/test_z2.py -v`.

## З4. Соединение на время запроса: `get_conn`

Допишите в `app/db.py`:

```python
def get_conn():
    with psycopg.connect(settings.database_url, row_factory=dict_row) as conn:
        yield conn
```

Это **зависимость с `yield`**: FastAPI вызывает функцию перед обработчиком, передает ему `conn`, а после обработчика продолжает функцию с места `yield`. Блок `with` у соединения psycopg:
- в конце блока подтверждает изменения (`COMMIT`);
- если внутри блока возникло исключение (например, `HTTPException` 404), отменяет их (`ROLLBACK`);
- в любом случае закрывает соединение.

`row_factory=dict_row` – строки результата приходят словарями `{"id": 1, "date": ...}`, а не кортежами. Такой словарь сразу подходит для модели ответа `TripOut`.

Обработчики получают соединение параметром `conn: Conn` (тип `Conn` уже объявлен в `db.py`). Посмотрите на готовый маршрут `/api/health` в `main.py`: так выглядит запрос к базе внутри обработчика.

Проверка: `pytest tests/test_z4.py`.

(Решение без недостатков – пул соединений – в Т4.Б3.2.) б) Что произойдет с поездкой, если после `INSERT` в обработчике возникнет исключение? в) Зачем у `Conn` указано `scope="function"`? ## З5. Программный интерфейс на SQL

Перепишите маршруты `/api/trips` из Т4.Б1.3 на запросы к таблице `trips`. Ответы программного интерфейса не меняются: клиенты (страница на React, мобильное приложение) не заметят перехода.

| Маршрут | Запрос | Особенность |
| --- | --- | --- |
| `GET /api/trips` | `SELECT ... WHERE ... ORDER BY ...` | фильтры и сортировка |
| `POST /api/trips` | `INSERT ... RETURNING ...` | номер и время создания выдает база |
| `GET /api/trips/{trip_id}` | `SELECT ... WHERE id = %s` | `fetchone()` вернул `None` – 404 |
| `PUT /api/trips/{trip_id}` | `UPDATE ... SET ... WHERE id = %(id)s RETURNING ...` | `None` – 404 |
| `DELETE /api/trips/{trip_id}` | `DELETE ... WHERE id = %s` | `cursor.rowcount == 0` – 404 |

**Знаки подстановки.** Значения от клиента передаются в запрос только знаками подстановки: `%s` (по порядку, значения – списком) или `%(имя)s` (по имени, значения – словарем):

```python
conn.execute("SELECT ... FROM trips WHERE id = %s", [trip_id])
conn.execute("INSERT ... VALUES (%(date)s, %(distance)s, ...)", trip.model_dump())
```

Это не форматирование строк Python: текст запроса и значения уходят на сервер PostgreSQL отдельно. **Никогда** не вставляйте значения в текст запроса через f-строку или `+`: почему это опасно, разберем в Т4.Б3.1. Единственное, что можно собирать в тексте, – готовые куски из своего кода: список столбцов `TRIP_COLUMNS` и порядок сортировки из словаря `ORDER_BY` (допишите его). Порядок сортировки знаком подстановки передать нельзя: подставлять можно только значения, а не части команды.

Методы курсора: `conn.execute(...)` возвращает курсор; `.fetchone()` – одна строка или `None`; `.fetchall()` – список строк; `.rowcount` – сколько строк изменила команда.

Проверка: `pytest tests/test_z5.py`, затем в `/docs` создайте поездку и найдите ее в psql: `SELECT * FROM trips;`.
